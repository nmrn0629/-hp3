## 却下候補リスト

ユーザーが調査モードで提示された候補を選択しなかった場合、その候補を却下リストに記録し、以降の調査で再提示しない。

- ファイル: `[作業ディレクトリ]/rejected-topics.json`
- 形式:
  ```json
  [
    {
      "url": "https://...",
      "title": "候補タイトル",
      "rejectedDate": "2026-05-05"
    }
  ]
  ```
- **有効期限: 3ヶ月（90日）**。調査モード実行時に `rejectedDate` から90日以上経過したエントリは自動的に削除してからフィルタリングに使用する。
- ファイルが存在しない場合は空配列 `[]` として扱う（エラーにしない）。
- 却下リストは git 管理対象外とする（`.gitignore` に含める）。初回実行時に `.gitignore` に `rejected-topics.json` が無ければ追加する。

---

1. 発火条件を判定する。
- ユーザーメッセージに更新指示があることを確認する。例: `TOPICSを更新して` `TOPICSに追加して` `トピックス更新`。
- あわせて、URLまたは話題の手がかりがあることを確認する。
- 更新指示がない場合はこのスキルを使わない。

2. TOPICS用URLを確定する。
- 最優先でユーザー提示URLを使う。
- URLが `https://` かつホストが `nta.go.jp` または `*.nta.go.jp` なら採用する。
- ユーザー提示URLが国税庁ドメイン以外なら、その話題に対応する国税庁ページをWeb検索またはWebFetchで特定し、採用URLを国税庁URLに置き換える。
- 国税庁の該当ページを特定できない場合は、ファイルを更新せず停止して理由を報告する。

3. トピック表示文言を取得する。
- 採用URLをWebFetchして、`<title>` を第一候補として取得する。
- `<title>` が不適切または空なら `h1` を使う。
- 前後空白を除去し、1行テキストに正規化する。
- JavaScript文字列として安全になるように `\\` `"` 改行をエスケープする。

4. 更新データを組み立てる。
- 日付は日本時間で `YYYY/MM/DD` 形式を使う。
- 新規エントリは以下3キーを必須にする: `date` `content` `url`。
- 既存配列に同一URLがある場合は重複追加せず、対象エントリを最新情報で更新して先頭へ移動する。
- 複数エントリを一度に追加する場合、国税庁ページの更新日・施行日が新しい順（降順）で先頭から並べる。
  - 例: 2月更新のページ → 1月更新のページ の順に配置する。
  - 同日の場合はユーザー提示の順（番号の若い順）とする。
- 履歴件数は先頭から最大20件に丸める。

5. `topics-data.js` を更新する。
- 対象: `[作業ディレクトリ]/js/topics-data.js`
- `const topicsData = [ ... ];` の配列を更新する。行番号固定で編集しない。
- 既存の公開処理は維持する。
  - `if (typeof window !== 'undefined') { window.topicsData = topicsData; }`
- 文字コードはUTF-8を維持し、不要な文字化けを起こさない。

6. `index.html` のキャッシュバージョンを更新する。
- 対象: `[作業ディレクトリ]/index.html`
- `<script src="js/topics-data.js?v=X.XX"></script>` を特定して `X.XX` を `+0.01` する。
- 浮動小数の誤差を避けるため、`X.XX` は「百分位の整数」として加算してから2桁固定で戻す。
  - 例: `1.01 -> 1.02`, `1.09 -> 1.10`, `1.99 -> 2.00`
- 該当scriptタグが見つからない場合は、ファイルを更新せず停止して報告する。

7. 更新後に検証する。
- `topics-data.js` が構文エラーでないことを確認する。
- `index.html` の `topics-data.js?v=` が更新前より増えていることを確認する。
- 失敗時は可能な限り変更を戻し、戻せない場合は差分を明示して報告する。

8. 完了報告を返す。
- 次を必ず含める: 採用した国税庁URL、TOPICS文言、日付、バージョン更新前後、重複処理の有無。
- 失敗時は「何が足りず停止したか」を具体的に示す。

## 実行時チェックリスト（手動更新モード）
- URLは国税庁ドメインか。
- `content` はJS文字列として安全か。
- 同一URLの重複追加をしていないか。
- `topics-data.js` と `index.html` の2ファイルのみを更新しているか。
- 変更結果をユーザーに明示したか。

## 調査モード（「TOPICSを調査して」で発火）

このモードは「TOPICSを調査して」「トピックスを調べて」などの指示でのみ発火する。
URLの手動提示がなくても自動で国税庁を調べる。

**停止点は2つだけとする。** それ以外の場面でユーザーに判断を求めて手を止めてはならない。

1. **候補の確認**（セクションB）— 調査から候補提示までは、途中で確認を挟まず一気に自動で進める。国税庁HPの閲覧について都度の許可を求めない。
2. **公開の確認**（セクションD手順3）— ファイル更新とローカルコミットまで進めた上で、main へのマージ・プッシュの直前に確認する。

### A. 調査は nta-investigator サブエージェントに必ず委譲する（デフォルト・必須）

調査モードでは、メイン側で直接 WebFetch / WebSearch を回してはならない。国税庁HPの調査は必ず `nta-investigator` サブエージェントに委譲する。

責務分界:
- サブエージェントの返却契約は **候補データのみ**（タイトル・URL・更新日）に限定する。
- ユーザーへの確認UIはサブエージェント側で作らない。確認UIはメイン側の責務であり、後述セクションBの `AskUserQuestion` で実施する。

サブエージェントに渡す除外リスト:
- `topics-data.js` に既に掲載済みのURL
- `rejected-topics.json` に記録されている却下済みURL（有効期限内のもの）
- この2つを合わせてサブエージェントのプロンプトに「除外URL一覧」として明示する。

サブエージェントが返す内容:
- 国税庁の最新税務情報の候補リスト（タイトル・URL・更新日）

サブエージェントが停止・失敗した場合はファイルを変更せず停止して報告する（メイン側でのフォールバック調査は行わない）。

### B. AskUserQuestion でユーザーに採用候補を選んでもらう（必須）

候補が1件以上見つかった場合は、**候補の件数にかかわらず必ず** `AskUserQuestion` ツールを呼び出してユーザーに採否を確認する。候補が1件だけでも選択ステップを省略してはならない。

ツール仕様に依存する具体値（オプション数上限、質問数上限、Otherの挙動、1ラウンドあたりの提示件数など）は、実装時点の `AskUserQuestion` ツール仕様に従って分割・提示する。本文には上限値をハードコードしない。

#### 候補一覧の提示（必須・`AskUserQuestion` を呼ぶ前に行う）

候補が1件以上あるときは、`AskUserQuestion` を呼ぶ前に、本文テキストで候補の**全件**を一覧提示する。ユーザーが実際のページを開いて中身を確かめてから選べるようにするための手順であり、省略してはならない。

- **すべての候補に、そのページへ飛べるリンクを付ける。** 優先度が低い候補でも、件数が多くても、リンクを省かない。
- リンクは Markdown 形式 `[表示文字](URL)` で書く。裸のURLを貼らない。表形式にする場合は、タイトルをリンクにするか、独立したリンク列を必ず設ける。
- 1候補につき最低限、次の4点を示す: **通し番号 / 日付 / タイトル / リンク**。加えて優先度と一言理由を添える。
- **優先度の低い候補をまとめて1行に詰め込まない。** 全候補を同じ粒度・同じ書式で示す。優先度でグループ分けするのはよいが、粒度は落とさない。
- 通し番号は `AskUserQuestion` の選択肢と一対一で対応させる。ユーザーが番号だけで採否を伝えられるようにするため。
- `AskUserQuestion` の `description` にもURLを文字列として含める（選択肢内ではリンクにならないため、一覧側のリンクが実質的な確認手段になる）。

#### B-0. 候補が0件のとき
「現時点で追加に値する新しい情報は見当たりませんでした」と報告して終了する。

#### B-1. 候補が1件のとき（共通ルールの例外）
`AskUserQuestion` を1回呼び出し、**候補1件に対応する「採用する／採用しない」の2択質問**で採否を確認する。
- この質問では `multiSelect` は使わず（単一選択）、`options` は「採用する」「採用しない」の2件構成とする。
- 各オプションの `description` に候補のタイトル・更新日・URLを含めて、何を採否するかをユーザーに明示する。
- 「採用する」選択 → 候補採用。「採用しない」または Other でキャンセル明示 → 終了。
- このB-1では、下記B-2の「`multiSelect: true`」「各option=1候補対応」のルールは**適用しない**。

#### B-2. 候補が2件以上のとき（共通ルール）
- `AskUserQuestion` の `multiSelect: true` を用いる（チェックボックス形式）。
- `question` は「採用するTOPICS候補を選んでください。」で統一。
- 各 `options` は1候補に対応させ、`label` は候補タイトル短縮、`description` には更新日とURLを含める。
- 「全部採用」のショートカット・オプションは追加しない（ユーザーがチェックした項目のみを採用する方式に統一）。
- 1回の呼び出しでツール仕様の上限を超える件数になる場合は、更新日降順に並べ替えた上で**複数ラウンドに分割して全候補を順次提示**する。切り捨てはしない。
  - **中間ラウンド（未提示候補が残っているラウンド）では、ユーザーに「先に確定する」選択肢を出さない**。中間ラウンドの末尾で立てる追加質問は「次のラウンドを表示する／キャンセルする」の2択のみに限定する（キャンセルは全体終了を意味する）。
  - **最終ラウンド（残候補0になった時点）**で初めて、そこまでに集約されたチェックの全体で確定してよい。未提示候補を残したままの確定は許可しない。

#### 選択結果の集約ルール
- B-1（1件時）: 「採用する」選択のみ採用、それ以外はキャンセル扱いで終了。
- B-2（複数件）: すべての質問・ラウンドの選択結果を和集合としてまとめる。中間ラウンドで「キャンセル」が選ばれた場合は即終了（ファイル変更なし）。全ラウンド完走後、採用候補が0件ならファイル変更せず終了、1件以上なら採用して続行。
- ユーザーが Other で「キャンセル」等を明示した場合はキャンセル扱いで終了。

### B-3. 未選択候補を却下リストに保存する

AskUserQuestion の全ラウンド完了後、**提示されたが選択されなかった候補**を `rejected-topics.json` に追加する。

- 各未選択候補について `url`、`title`、`rejectedDate`（実行日、YYYY-MM-DD形式）を記録する。
- 既に同一URLが却下リストにある場合は `rejectedDate` を今回の実行日で上書きする（期限リセット）。
- 保存後、有効期限切れ（90日超）のエントリがあれば削除してからファイルに書き戻す。
- ユーザーがキャンセルした場合（候補0件で終了含む）も、提示済み候補は却下リストに追加する。

### C. 承認された候補でファイルを更新する

上記ステップ2〜6と同じ手順で `topics-data.js` と `index.html` を更新する。
複数候補が承認された場合は、国税庁ページの更新日・施行日が新しい順（降順）で先頭から並べる。同日の場合は番号の若い順とする。

### D. GitHub ブランチを作成して main にマージする

作業ディレクトリ: 上記「パス解決」セクションで判定したディレクトリを使用する

1. ブランチを作成する（YYYYMMDD は実行日、例: 20260325）:
   ```bash
   git checkout -b topics-update-YYYYMMDD
   ```
2. 変更をステージしてコミットする:
   ```bash
   git add js/topics-data.js index.html
   git commit -m "Update TOPICS: [承認されたトピックのタイトルをカンマ区切りで列記]"
   ```
3. **【公開前の確認ゲート／必須】** ここでいったん停止し、`AskUserQuestion` でユーザーに公開の可否を確認する。ここから先は公開ホームページの内容を書き換える操作であり、ユーザーの明示的な承認なしに進めてはならない。
   - 確認前に、これから公開される内容を提示する: 追加したトピックの一覧（日付・文言・URL）、`index.html` のバージョン変更（前→後）、`git diff --stat` の結果、ローカルコミットのハッシュ。
   - `question` は「この内容で公開（main へマージ・プッシュ）してよいですか？」とし、`multiSelect` は使わない（単一選択）。
   - `options` は次の2件構成にする。
     - 「公開する」→ 手順4以降に進む。
     - 「ローカルコミットまでで止める」→ push・マージを行わず終了する。作業ブランチはローカルに残し、ブランチ名・コミットハッシュと、後から公開する場合のコマンドを報告する。
   - Other でキャンセルが明示された場合も、push・マージを行わず終了する。
   - 承認が得られた場合のみ、作業ブランチをリモートにプッシュする:
   ```bash
   git push origin topics-update-YYYYMMDD
   ```
4. main にマージしてリモートにプッシュする:
   ```bash
   git checkout main
   git merge --no-ff topics-update-YYYYMMDD -m "Merge topics-update-YYYYMMDD into main"
   git push origin main
   ```
5. 作業ブランチをローカル削除する（クリーンアップ）:
   ```bash
   git branch -d topics-update-YYYYMMDD
   ```

### D完了報告に含める内容
- 採用されたトピック一覧（タイトル・URL・日付）
- 作成した GitHub ブランチ名
- コミットメッセージ
- main へのマージ・プッシュ完了の確認

## 調査モード チェックリスト
- 「TOPICSを調査して」系の指示か（手動URLあり指示との混同を避ける）。
- 調査は `nta-investigator` サブエージェントに委譲したか（メイン側で直接 WebFetch/WebSearch を回していないか）。
- 調査から候補提示までの間、確認を挟まず自動で進めたか（停止点は「候補の確認」と「公開の確認」の2つだけか）。
- サブエージェントに渡す除外リストに、掲載済みURLと却下リスト（有効期限内）の両方を含めたか。
- 候補はすべて国税庁ドメイン（nta.go.jp）か。
- `AskUserQuestion` の前に、候補の全件を本文で一覧提示したか。
- **全候補にページへ飛べる Markdown リンクを付けたか**（優先度の低い候補を1行に詰め込んでリンクを落としていないか）。
- 候補が1件以上あるとき、`AskUserQuestion` を必ず使ってユーザーに選択させたか。
- 候補が1件のときは「採用する／採用しない」の単一選択2択質問で採否を確認したか（共通ルールの例外として処理したか）。
- 候補が2件以上のときは `multiSelect: true` で提示し、ツール仕様の上限を超える場合は複数ラウンドに分割して**全候補**をユーザーに提示したか（切り捨ては行っていないか）。
- 中間ラウンドでは「先に確定する」選択肢を出さず、「次のラウンドを表示／キャンセル」のみにとどめたか。
- 最終ラウンド送信（未提示候補0）のタイミングでのみ確定を行ったか。
- すべての質問・ラウンドの選択結果を和集合で集約して採用対象を確定したか。
- 採用候補が0件（キャンセル明示を含む）だった場合は、ファイルを変更せずに終了したか。
- 未選択候補を `rejected-topics.json` に保存したか（有効期限切れエントリの削除も含む）。
- `rejected-topics.json` が `.gitignore` に含まれているか（初回実行時に確認・追加）。
- git 操作は `topics-data.js` と `index.html` の2ファイルのみをステージしているか（`rejected-topics.json` はステージしない）。
- ブランチ名に実行日（YYYYMMDD）が入っているか。
- ローカルコミット後、push の前に `AskUserQuestion` で公開の可否を確認したか（無断で push・マージしていないか）。
- 公開が承認された場合のみ、main へのマージ・リモートプッシュまで完了したか。承認されなかった場合はローカルブランチを残して終了し、後から公開するコマンドを報告したか。
