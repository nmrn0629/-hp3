|---|---|

## 却下候補リスト

ユーザーが調査モードで提示された候補を選択しなかった場合、その候補を却下リストに記録し、以降の調査で再提示しない。

- ファイル: `[作業ディレクトリ]/rejected-topics.json`
- 形式:
  ```json
  [
    {
      "url": "https://...",
      "title": "候補タイトル",
      "rejectedDate": "2026-05-05"
    }
  ]
  ```
- **有効期限: 3ヶ月（90日）**。調査モード実行時に `rejectedDate` から90日以上経過したエントリは自動的に削除してからフィルタリングに使用する。
- ファイルが存在しない場合は空配列 `[]` として扱う（エラーにしない）。
- 却下リストは git 管理対象外とする（`.gitignore` に含める）。初回実行時に `.gitignore` に `rejected-topics.json` が無ければ追加する。

---

1. 発火条件を判定する。
- ユーザーメッセージに更新指示があることを確認する。例: `TOPICSを更新して` `TOPICSに追加して` `トピックス更新`。
- あわせて、URLまたは話題の手がかりがあることを確認する。
- 更新指示がない場合はこのスキルを使わない。

2. TOPICS用URLを確定する。
- 最優先でユーザー提示URLを使う。
- URLが `https://` かつホストが `nta.go.jp` または `*.nta.go.jp` なら採用する。
- ユーザー提示URLが国税庁ドメイン以外なら、その話題に対応する国税庁ページをWeb検索またはWebFetchで特定し、採用URLを国税庁URLに置き換える。
- 国税庁の該当ページを特定できない場合は、ファイルを更新せず停止して理由を報告する。

3. トピック表示文言を取得する。
- 採用URLをセクションA-2の方法で取得して、`<title>` を第一候補として取得する。
- `<title>` が不適切または空なら `h1` を使う。
- 前後空白を除去し、1行テキストに正規化する。
- JavaScript文字列として安全になるように `\\` `"` 改行をエスケープする。

4. 更新データを組み立てる。
- 日付は日本時間で `YYYY/MM/DD` 形式を使う。
- 新規エントリは以下5キーを必須にする: `date` `dateType` `content` `url` `addedAt`。
  - `dateType` は `date` が何の日付かを示す区分で、`発出日` `掲載日` `実施日` のいずれか。ホームページ上で日付の横に「（発出日）」とカッコ書きで表示される。
    - `発出日` … 法令解釈通達・事務運営指針・国税庁告示
    - `掲載日` … パンフレット・手引・FAQ・お知らせ・案内ページなど
    - `実施日` … 様式変更など、掲載日ではなく「これから変更が始まる日」を採った場合
  - 調査モードでは、セクションA-6で決めた `dateType` をそのまま使う。手動更新モードでも同じ決め方で判断する。
  - **既存エントリの `dateType` は書き換えない。** 過去分は旧方針（掲載日）のまま残っているものがあり、機械的に付け替えると誤表示になる。
  - `addedAt` は **サイトに追加した日時**（日本時間・ISO 8601、例: `"2026-10-17T12:22:09+09:00"`）。トップページでは `addedAt` から24時間だけ「NEW」を表示する（`script.js` の `isNewTopic`）。
    - `date`（国税庁側の日付）とは別物。古い日付のトピックを今日追加しても、追加から24時間は「NEW」になる。
    - 値は `topics-data.js` を更新するときの現在時刻（`TZ=Asia/Tokyo date +%Y-%m-%dT%H:%M:%S+09:00`）。一度に追加する複数件は同じ値でよい。
    - 公開（main へのプッシュ）を後日に回した場合は、公開の直前に今回追加分の `addedAt` を公開時刻へ付け直す。そうしないと公開した時点で24時間を過ぎていることがある。
    - 既存エントリに `addedAt` を後から付け足さない（付いていないものは「NEW」にならないだけで問題ない）。
- 既存配列に同一URLがある場合は重複追加せず、対象エントリを最新情報で更新して先頭へ移動する。このとき `addedAt` も今回の日時に付け直す。
- 複数エントリを一度に追加する場合、国税庁ページの更新日・施行日が新しい順（降順）で先頭から並べる。
  - 例: 2月更新のページ → 1月更新のページ の順に配置する。
  - 同日の場合はユーザー提示の順（番号の若い順）とする。
- 履歴件数は先頭から最大20件に丸める。21件目以降は捨てずに、`topicsArchiveData = topicsData.concat([ ... ])` の配列の先頭へ移す（過去のTOPICSページで引き続き表示するため）。

5. `topics-data.js` を更新する。
- 対象: `[作業ディレクトリ]/js/topics-data.js`
- `const topicsData = [ ... ];` の配列を更新する。行番号固定で編集しない。
- 既存の公開処理は維持する。
  - `if (typeof window !== 'undefined') { window.topicsData = topicsData; }`
- 文字コードはUTF-8を維持し、不要な文字化けを起こさない。

6. キャッシュバージョンを更新する。
- 対象は **`topics-data.js` を読み込んでいる全HTML**。ファイル名を決め打ちせず、毎回 `grep -l 'js/topics-data.js?v=' *.html` で洗い出す（2026-10-17時点で `index.html` `archive.html` `manager-topics.html` `about.html` `contact.html` `pricing.html` `privacy.html` `services.html` の8ファイル）。
  - どのページにも浮遊TOPICSがあり、一部だけを加算すると残りのページが古いキャッシュを読み続けて表示が食い違う（2026-09-20に `v=1.20`、2026-10-17に5ページが `v=1.35` のまま取り残されていた実績あり）。
- 各ファイルの `<script src="js/topics-data.js?v=X.XX"></script>` を特定して `X.XX` を `+0.01` する。
- 全ファイルのバージョンは常に同じ値に揃える。値がバラバラな場合は、最も大きい値を基準に `+0.01` して全ファイルを同じ値にする。
- 浮動小数の誤差を避けるため、`X.XX` は「百分位の整数」として加算してから2桁固定で戻す。
  - 例: `1.01 -> 1.02`, `1.09 -> 1.10`, `1.99 -> 2.00`
- 該当scriptタグが見つからない場合は、ファイルを更新せず停止して報告する。

7. 更新後に検証する。
- `topics-data.js` が構文エラーでないことを確認する。
- 対象の全HTMLの `topics-data.js?v=` が、すべて同じ値かつ更新前より増えていることを確認する。
- 今回追加したエントリすべてに `addedAt` が付いていることを確認する。
- 失敗時は可能な限り変更を戻し、戻せない場合は差分を明示して報告する。

8. 完了報告を返す。
- 次を必ず含める: 採用した国税庁URL、TOPICS文言、日付、`addedAt`（「NEW」が消える日時の目安）、バージョン更新前後、重複処理の有無。
- 失敗時は「何が足りず停止したか」を具体的に示す。

## 実行時チェックリスト（手動更新モード）
- URLは国税庁ドメインか。
- `content` はJS文字列として安全か。
- 同一URLの重複追加をしていないか。
- `topics-data.js` と、キャッシュバージョン対象のHTML（`topics-data.js` を読み込む全HTML）のみを更新しているか。
- 新規エントリに `addedAt`（サイトに追加した日時）を付けたか。
- 変更結果をユーザーに明示したか。

## 調査モード（「TOPICSを調査して」で発火）

このモードは「TOPICSを調査して」「トピックスを調べて」などの指示でのみ発火する。
URLの手動提示がなくても自動で国税庁を調べる。

**停止点は2つだけとする。** それ以外の場面でユーザーに判断を求めて手を止めてはならない。

1. **候補の確認**（セクションB）— 調査から候補提示までは、途中で確認を挟まず一気に自動で進める。国税庁HPの閲覧について都度の許可を求めない。
2. **公開の確認**（セクションD手順3）— ファイル更新とローカルコミットまで進めた上で、main へのマージ・プッシュの直前に確認する。

### A. 調査はサブエージェントを使わず、自分で行う（必須）

調査モードでは**サブエージェントを使わない。** 調査用のエージェントだけでなく、`web-fetch` のようなページ取得の代行エージェントも使わない。一覧ページの確認から候補の確定まで、このスキルを実行しているエージェント自身が行う。

#### A-1. 除外URLを揃える

次の2つを合わせて「除外URL一覧」とし、ここに含まれるURLは候補にしない。

- `js/topics-data.js` に既に掲載済みのURL（`topicsData` と `topicsArchiveData` の両方）
- `rejected-topics.json` に記録されている却下済みURL（有効期限内のもの）

`rejected-topics.json` は git 管理外なので、git worktree の中には存在しない。worktree で作業しているときも、上記「パス解決」の作業ディレクトリにある本体のファイルを読み書きする。

#### A-2. ページを取得する

国税庁のページには UTF-8 と Shift_JIS が混在しており、WebFetch などで取得すると Shift_JIS のページが文字化けして読めないことがある（2026-10-30 に通達の本文が読めず、発出日が推定になった実績あり）。そのため、次のコマンドで取得し、タグを除いたテキストとして読む。文字コードは自動で判定し、リンクは `リンク文字 [リンク先]` の形で残る。`URL` の部分を読みたいページに置き換える。

```bash
curl -sL -m 20 "URL" | python3 -I -c '
import re, sys
b = sys.stdin.buffer.read()
try:
    t = b.decode("utf-8")
except UnicodeDecodeError:
    t = b.decode("cp932", "replace")
t = re.sub(r"<!--.*?-->|<(script|style)\b.*?</\1>", "", t, flags=re.S | re.I)
t = re.sub(r"<a\b[^>]*href=\"([^\"]+)\"[^>]*>(.*?)</a>", r"\2 [\1]", t, flags=re.S | re.I)
t = re.sub(r"<[^>]+>", " ", t)
print(re.sub(r"\s*\n\s*", "\n", re.sub(r"[ \t\r\f\v]+", " ", t)).strip())
'
```

- `curl` や `python3` が使えない環境では、WebFetch など直接使えるWeb取得ツールで読む。
- 一覧で見つからないページを探すときは、Web検索も使ってよい。

#### A-3. 調査対象を確認する

**前回のTOPICS更新の数日前から今日まで**を重点に、次の一覧ページを確認する。前回の更新日は `git log -1 --date=short --pretty='%ad %h %s'` などで本体リポジトリの履歴から確かめる（Claude側とCodex側の2系統が同じファイルを更新しているため）。

1. トップページの新着情報: `https://www.nta.go.jp/`（トピックス、法令等などの分類ごとに日付付きで並ぶ）
2. トピックス一覧: `https://www.nta.go.jp/information/news/index.htm`
3. 報道発表: `https://www.nta.go.jp/information/release/index.htm`
4. 法令解釈通達: `https://www.nta.go.jp/law/tsutatsu/menu.htm`
5. パンフレット・手引: `https://www.nta.go.jp/publication/pamph/01.htm`
6. e-Taxのお知らせ一覧: `https://www.e-tax.nta.go.jp/topics/index.htm`

ページが404や取得失敗の場合は、別の入口（トップページの新着一覧、サイト内検索など）を試す。国税庁のページは見つからないときも HTTP 200 で「指定されたページを表示できませんでした」と返すことがあるので、ステータスではなく本文で判断する。
それでも調査が成り立たない場合は、ファイルを変更せず停止して報告する。

#### A-4. タイトルと実在を確認する

実ページの `<title>` が「A2 源泉所得税関係」のように区分名だけで、TOPICS表示に使えないことがある。そのため、**TOPICS表示に使うタイトルは、原則として一覧ページに記載された正式名称を採用する。** 実ページの `<title>` は裏取りに使う。

1. 一覧ページから、掲載名称・掲載日・リンク先URLを取る。
2. 調査期間内で除外URLに含まれないものは、リンク先を取得し、実在することと、内容が一覧の名称と矛盾しないことを確認する。
3. 判定する。
   - 取得できない、取得内容が空、または「指定されたページを表示できませんでした」と表示される → 候補にしない
   - 内容が一覧の名称と明らかに矛盾する、または文字化けして判読できない → 候補にしない
   - 実ページの `<title>` が区分名などで表示に不適 → 一覧の名称を採用する
4. タイトル末尾の `｜国税庁` は削除し、TOPICS表示用の1行テキストに整える。
5. URLに `xx` などのプレースホルダらしき文字列が含まれる場合は、本文まで読んで実在するページか確認する（`.../kaisei/2606xx/index.htm` のように実在する例もある）。

#### A-5. 候補ごとに次の情報をまとめる

- タイトル: 一覧ページの正式名称（一覧に無い場合は実ページの `<title>`、それも不適なら `h1`）
- URL
- `date`（`YYYY/MM/DD`）と `dateType`: 下記A-6に従って決める。判明しない場合は両方とも空欄にする
- 日付の根拠（例「通達本文に課資6-84 令和8年6月30日と明記」「トップページ新着情報に令和8年7月13日と明記」）
- 優先度と、TOPICS候補として妥当な理由

候補は日付が新しい順に並べ、同日の場合は重要度順にする。**件数の上限は設けない。** 条件に合う候補はすべてユーザーに提示し、件数の都合で切り捨てない。

#### A-6. 日付の採り方

`dateType` は `date` の決め方と必ず一致させる。

- `発出日` … 法令解釈通達・事務運営指針・国税庁告示（通達本文の発出日を採ったもの）
- `掲載日` … パンフレット・手引・FAQ・お知らせ・案内ページなど（HPに掲載された日を採ったもの）
- `実施日` … 様式変更など、掲載日ではなく「これから変更が始まる日」を採ったもの

**法令解釈通達・事務運営指針・国税庁告示は、HPへの掲載日ではなく「通達の発出日」を採る。** 発出日は通達本文の冒頭（発信者・宛先の直前）に記載されている。例:

```
課資６−84
課評１−29
令和８年６月30日
各国税局長　殿
```

この場合、HPの新着一覧に令和8年7月9日と載っていても `date` は `2026/06/30` とする。URLのパスにも発出日が埋め込まれていることが多い（`.../kaisei/260617/` → 令和8年6月17日）ので、本文の記載と突き合わせて確認する。本文が読めない場合はURLのパスを根拠にしてよいが、その旨を日付の根拠に書く。

パンフレット・手引・FAQ・お知らせなど通達以外のものは発出日という概念がないため、HPの新着一覧に載っている掲載日（それが無ければPDFの発行年月）を採る。一覧の発行年月と実ファイルの更新日がずれている場合は、一覧の掲載日を採る。

ページにも一覧にも掲載日・更新日が見つからない場合は、次を上から順に試し、最初に当てはまったものを採る。**いずれの場合も、日付の根拠に「推測」である旨と理由を必ず書く。**

1. **年月までしか分からない場合は、その月の末日に丸める。** 例: 令和8年8月 → `2026/08/31`。
2. **週次一覧で範囲までしか絞れない場合は、その範囲の初日を採る。** 例: 8/17〜8/21の週次一覧には無く、8/24〜8/28の週次一覧に初出 → `2026/08/24`。新しさを過大表示しないための安全側の選択。
3. **ページ自体は古いが、そこに将来の施行日・実施日が明記されている場合は、その施行日・実施日を採ってよい。** ただしこれは掲載日ではないので、その旨を根拠に明記する。調査日より後の未来日になる場合は、候補一覧で**必ず指摘する**。
4. 上記のいずれでも決められない場合は `date` を空欄にし、根拠に「特定不可」と書く。**日付を捏造しない。**

#### A-7. 候補を選ぶ

優先度が高いもの:

- 直近1〜3か月以内に更新・公開されたもの
- 消費税、インボイス制度、所得税、確定申告、法人税、年末調整、電子帳簿保存法、税制改正に関するもの
- ハーモグロー会計事務所の一般的なクライアントに関係が深いもの

除外するもの:

- 除外URL一覧に含まれるもの
- `nta.go.jp` または `*.nta.go.jp` 以外のURL
- 3か月以上前の更新で新規性が弱いもの
- 酒税、たばこ税など一般クライアントに関係が薄い税目
- 内部的な会議の配付資料、統計整備検討会、共同研究会議の資料
- 一時的な障害告知・その解消告知
- 職員採用、入札公告、調達情報

#### A-8. URLのルール

- 候補のURLは必ず `nta.go.jp` または `*.nta.go.jp` 配下に限定する。国税庁外の解説サイト、SNS、検索結果URLは候補にしない。
- **候補のURLは必ずHTMLページにする。`.pdf` で終わるURLを候補にしてはならない。** 候補を確認する側の環境ではPDFのURLを開けず、中身を確かめられないため採否を判断できない。
  - PDFしか実体がない資料は、そのPDFを掲載している**親のHTMLページ**（特設サイト、パンフレット一覧、コーナーページ、お知らせページなど）のURLに置き換える。名称・掲載日はリンク元の一覧ページの記載を根拠にする。
  - 置き換え先の親ページが除外URL一覧に既にある場合は、重複掲載になるため候補にしない。
  - 親ページも独立したHTMLページも存在しない資料は、候補から落とす。

### B. AskUserQuestion でユーザーに採用候補を選んでもらう（必須）

候補が1件以上見つかった場合は、**候補の件数にかかわらず必ず** `AskUserQuestion` ツールを呼び出してユーザーに採否を確認する。候補が1件だけでも選択ステップを省略してはならない。

ツール仕様に依存する具体値（オプション数上限、質問数上限、Otherの挙動、1ラウンドあたりの提示件数など）は、実装時点の `AskUserQuestion` ツール仕様に従って分割・提示する。本文には上限値をハードコードしない。

#### 候補一覧の提示（必須・`AskUserQuestion` を呼ぶ前に行う）

候補が1件以上あるときは、`AskUserQuestion` を呼ぶ前に、本文テキストで候補の**全件**を一覧提示する。ユーザーが実際のページを開いて中身を確かめてから選べるようにするための手順であり、省略してはならない。

- **すべての候補に、そのページへ飛べるリンクを付ける。** 優先度が低い候補でも、件数が多くても、リンクを省かない。
- リンクは Markdown 形式 `[表示文字](URL)` で書く。裸のURLを貼らない。表形式にする場合は、タイトルをリンクにするか、独立したリンク列を必ず設ける。
- 1候補につき最低限、次の4点を示す: **通し番号 / 日付 / タイトル / リンク**。加えて優先度と一言理由を添える。
- **優先度の低い候補をまとめて1行に詰め込まない。** 全候補を同じ粒度・同じ書式で示す。優先度でグループ分けするのはよいが、粒度は落とさない。
- 通し番号は `AskUserQuestion` の選択肢と一対一で対応させる。ユーザーが番号だけで採否を伝えられるようにするため。
- `AskUserQuestion` の `description` にもURLを文字列として含める（選択肢内ではリンクにならないため、一覧側のリンクが実質的な確認手段になる）。

#### B-0. 候補が0件のとき
「現時点で追加に値する新しい情報は見当たりませんでした」と報告して終了する。

#### B-1. 候補が1件のとき（共通ルールの例外）
`AskUserQuestion` を1回呼び出し、**候補1件に対応する「採用する／採用しない」の2択質問**で採否を確認する。
- この質問では `multiSelect` は使わず（単一選択）、`options` は「採用する」「採用しない」の2件構成とする。
- 各オプションの `description` に候補のタイトル・更新日・URLを含めて、何を採否するかをユーザーに明示する。
- 「採用する」選択 → 候補採用。「採用しない」または Other でキャンセル明示 → 終了。
- このB-1では、下記B-2の「`multiSelect: true`」「各option=1候補対応」のルールは**適用しない**。

#### B-2. 候補が2件以上のとき（共通ルール）
- `AskUserQuestion` の `multiSelect: true` を用いる（チェックボックス形式）。
- `question` は「採用するTOPICS候補を選んでください。」で統一。
- 各 `options` は1候補に対応させ、`label` は候補タイトル短縮、`description` には更新日とURLを含める。
- 「全部採用」のショートカット・オプションは追加しない（ユーザーがチェックした項目のみを採用する方式に統一）。
- 1回の呼び出しでツール仕様の上限を超える件数になる場合は、更新日降順に並べ替えた上で**複数ラウンドに分割して全候補を順次提示**する。切り捨てはしない。
  - **中間ラウンド（未提示候補が残っているラウンド）では、ユーザーに「先に確定する」選択肢を出さない**。中間ラウンドの末尾で立てる追加質問は「次のラウンドを表示する／キャンセルする」の2択のみに限定する（キャンセルは全体終了を意味する）。
  - **最終ラウンド（残候補0になった時点）**で初めて、そこまでに集約されたチェックの全体で確定してよい。未提示候補を残したままの確定は許可しない。

#### 選択結果の集約ルール
- B-1（1件時）: 「採用する」選択のみ採用、それ以外はキャンセル扱いで終了。
- B-2（複数件）: すべての質問・ラウンドの選択結果を和集合としてまとめる。中間ラウンドで「キャンセル」が選ばれた場合は即終了（ファイル変更なし）。全ラウンド完走後、採用候補が0件ならファイル変更せず終了、1件以上なら採用して続行。
- ユーザーが Other で「キャンセル」等を明示した場合はキャンセル扱いで終了。

### B-3. 未選択候補を却下リストに保存する

AskUserQuestion の全ラウンド完了後、**提示されたが選択されなかった候補**を `rejected-topics.json` に追加する。

- 各未選択候補について `url`、`title`、`rejectedDate`（実行日、YYYY-MM-DD形式）を記録する。
- 既に同一URLが却下リストにある場合は `rejectedDate` を今回の実行日で上書きする（期限リセット）。
- 保存後、有効期限切れ（90日超）のエントリがあれば削除してからファイルに書き戻す。
- ユーザーがキャンセルした場合（候補0件で終了含む）も、提示済み候補は却下リストに追加する。

### C. 承認された候補でファイルを更新する

上記ステップ2〜6と同じ手順で `topics-data.js` と、キャッシュバージョン対象のHTML（`topics-data.js` を読み込む全HTML）を更新する。
TOPICSの文言は、ステップ3で取り直さず、セクションA-4で確定したタイトルを使う。
複数候補が承認された場合は、国税庁ページの更新日・施行日が新しい順（降順）で先頭から並べる。同日の場合は番号の若い順とする。

### D. GitHub ブランチを作成して main にマージする

作業ディレクトリ: 上記「パス解決」セクションで判定したディレクトリを使用する

1. ブランチを作成する（YYYYMMDD は実行日、例: 20260325）:
   ```bash
   git checkout -b topics-update-YYYYMMDD
   ```
2. 変更をステージしてコミットする:
   ```bash
   git add js/topics-data.js $(grep -l 'js/topics-data.js?v=' *.html)
   git commit -m "Update TOPICS: [承認されたトピックのタイトルをカンマ区切りで列記]"
   ```
3. **【公開前の確認ゲート／必須】** ここでいったん停止し、`AskUserQuestion` でユーザーに公開の可否を確認する。ここから先は公開ホームページの内容を書き換える操作であり、ユーザーの明示的な承認なしに進めてはならない。
   - 確認前に、これから公開される内容を提示する: 追加したトピックの一覧（日付・文言・URL）、キャッシュバージョンの変更（前→後。対象の全HTMLで揃っていること）、`git diff --stat` の結果、ローカルコミットのハッシュ。
   - `question` は「この内容で公開（main へマージ・プッシュ）してよいですか？」とし、`multiSelect` は使わない（単一選択）。
   - `options` は次の2件構成にする。
     - 「公開する」→ 手順4以降に進む。
     - 「ローカルコミットまでで止める」→ push・マージを行わず終了する。作業ブランチはローカルに残し、ブランチ名・コミットハッシュと、後から公開する場合のコマンドを報告する。
   - Other でキャンセルが明示された場合も、push・マージを行わず終了する。
   - 承認が得られた場合のみ、作業ブランチをリモートにプッシュする:
   ```bash
   git push origin topics-update-YYYYMMDD
   ```
4. main にマージしてリモートにプッシュする:
   ```bash
   git checkout main
   git merge --no-ff topics-update-YYYYMMDD -m "Merge topics-update-YYYYMMDD into main"
   git push origin main
   ```
5. 作業ブランチをローカル削除する（クリーンアップ）:
   ```bash
   git branch -d topics-update-YYYYMMDD
   ```

### D完了報告に含める内容
- 採用されたトピック一覧（タイトル・URL・日付）
- 作成した GitHub ブランチ名
- コミットメッセージ
- main へのマージ・プッシュ完了の確認

## 調査モード チェックリスト
- 「TOPICSを調査して」系の指示か（手動URLあり指示との混同を避ける）。
- 調査をサブエージェントに任せず、自分で行ったか（ページ取得の代行エージェントも使っていないか）。
- 調査から候補提示までの間、確認を挟まず自動で進めたか（停止点は「候補の確認」と「公開の確認」の2つだけか）。
- 除外URL一覧に、掲載済みURLと却下リスト（有効期限内）の両方を含めたか。
- 候補の実ページを取得し、実在と内容を確かめたか。
- 通達類の日付は、本文の発出日を確かめて採ったか。
- 候補はすべて国税庁ドメイン（nta.go.jp）のHTMLページか。
- `AskUserQuestion` の前に、候補の全件を本文で一覧提示したか。
- **全候補にページへ飛べる Markdown リンクを付けたか**（優先度の低い候補を1行に詰め込んでリンクを落としていないか）。
- 候補が1件以上あるとき、`AskUserQuestion` を必ず使ってユーザーに選択させたか。
- 候補が1件のときは「採用する／採用しない」の単一選択2択質問で採否を確認したか（共通ルールの例外として処理したか）。
- 候補が2件以上のときは `multiSelect: true` で提示し、ツール仕様の上限を超える場合は複数ラウンドに分割して**全候補**をユーザーに提示したか（切り捨ては行っていないか）。
- 中間ラウンドでは「先に確定する」選択肢を出さず、「次のラウンドを表示／キャンセル」のみにとどめたか。
- 最終ラウンド送信（未提示候補0）のタイミングでのみ確定を行ったか。
- すべての質問・ラウンドの選択結果を和集合で集約して採用対象を確定したか。
- 採用候補が0件（キャンセル明示を含む）だった場合は、ファイルを変更せずに終了したか。
- 未選択候補を `rejected-topics.json` に保存したか（有効期限切れエントリの削除も含む）。
- `rejected-topics.json` が `.gitignore` に含まれているか（初回実行時に確認・追加）。
- git 操作は `topics-data.js` と、キャッシュバージョン対象のHTMLのみをステージしているか（`rejected-topics.json` はステージしない）。
- 公開を後日に回した場合、公開の直前に今回追加分の `addedAt` を公開時刻へ付け直したか。
- 新規エントリに `dateType` を付けたか。既存エントリの `dateType` を書き換えていないか。
- ブランチ名に実行日（YYYYMMDD）が入っているか。
- ローカルコミット後、push の前に `AskUserQuestion` で公開の可否を確認したか（無断で push・マージしていないか）。
- 公開が承認された場合のみ、main へのマージ・リモートプッシュまで完了したか。承認されなかった場合はローカルブランチを残して終了し、後から公開するコマンドを報告したか。
